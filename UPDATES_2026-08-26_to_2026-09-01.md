## Read this first — five things need a decision

None of these are blocked on code. Each is a business call or a data fix
outside this repo.

### 1. Captured leads reach nobody

`deliverQuoteRequest()` in `services/quote.service.ts` is still a stub, so guest
details are written to the visitor's own `localStorage` and nowhere else. Sales
cannot follow up on any of it.

This matters more now than it did last week: the quote modal says *"we'll price
this container for your address"* and collects a validated address to do it. The
form is making a promise nothing can currently keep.

### 2. The PDP subtotal and the cart disagree

The PDP folds delivery into the subtotal for purchases. The cart takes shipping
from the backend's `get-total` — a different system, which returns 0 until
checkout knows a ZIP.

So a visitor sees **$4,950** on the product page, clicks Add to cart, and the
cart shows **$4,500**. Either pass the PDP figure through, or have `get-total`
read the same source.

### 3. Most products have no depot, so no rate can ever be quoted

Sampling 12 products against a ZIP *in their own city*, only 4 resolved a depot.
The rest return no distance and no rate whatever the visitor types — Orlando
products fail even at ZIP 32801, the depot's own city.

Confirmed upstream: calling the legacy `calculated_rates` action directly for
those items returns `{"result":null}`. The headless API is reporting this
faithfully; the gap is in the WooCommerce product data.

### 4. Your API and onsitestorage.com quote different delivery prices

The legacy page sends a two-letter state code; the new endpoint defaults to the
city resolved from the ZIP. Same container, same ZIP:

| Source | Distance | Rate |
|---|---|---|
| Legacy site (state code) | 209.67 mi | withheld as call-for-rate |
| New API (city) | 87.09 mi | **$609.63 quoted** |

The new one is accurate — SF depot to Sacramento really is ~87 miles; the state
code geocodes to roughly the state centroid. Which means the live site is
probably losing quotable orders to a geocoding artifact. Worth telling whoever
owns the WP plugin.

### 5. "(151 reviews)" links to the page it sits on

The Google Business Profile URL is not recorded anywhere in the repo, and a wrong
Google link sends customers to a different business. It points at the on-page
section until the real one is supplied — one line in `config/reviews.ts`.

Related: the mobile design says "200+ Reviews" while that config says 151. If
200+ is the real figure, the config is stale and the reviews section is
understating it too.

## Delivery pricing, live from WordPress

A service over the WordPress `calculated_rates` endpoint, which is still the
system of record for delivery. The PDP summary now shows a real rate, the
delivery method that produced it, and the distance behind it, instead of
"Calculated at checkout".

- `services/delivery.service.ts` — `fetchDeliveryRates()` (raw, never throws) and
  `getDeliveryRates()` (cached, `hours`, tagged `PRODUCTS`)
- `lib/delivery.ts` — readers, kept out of the service because a module holding
  `'use cache'` cannot be imported by a Client Component
- `app/api/delivery-rates/route.ts` — proxy so the browser never sees the WP origin
- `hooks/useDeliveryRates.ts` — debounced, aborts in flight, drops stale replies

**A trap worth knowing:** `rates_available: true` does not mean there is a price.
A 2,910-mile route comes back `true` with every rate `null` and
`call_for_rate: true`, because anything over $1,000 is withheld upstream in
favour of a phone call. `hasQuotedDelivery()` is the check you actually want.

**Delivery is only in the subtotal for outright purchases.** Rent and
rent-to-own quote a *monthly* figure while delivery is one-time — folding it in
would read "$967.84/mo" and overstate every month after the first. Rent also
already includes delivery. It still shows on those tabs, marked *one-time*.

**Delivery multiplies by quantity.** A tilt bed carries one container, so three
containers is three trips. Upstream always quotes for one and takes no quantity
parameter, so this is an approximation.

## Knowing where the visitor is

### The ZIP prompt

`ZipGateModal` — the "Get the Best Price on Your Container!" popup, on arrival.
Opens only when nothing else has answered: no `?zipcode=` in the URL and nothing
in storage from a previous visit or the geolocation detector. Anyone arriving
from the homepage or listing lookup never sees it.

Resolving reuses `useGeoapify`'s `selectResult`, so a ZIP entered there lands in
the same three storage keys as one entered anywhere else, depot included. On a
reference listing it also swaps the page onto the real container near the
visitor, which is the only thing that makes answering there worth anything.

### One source for the ZIP

`lib/visitorZip.ts` now answers "where is this visitor" once, with the **URL
winning over storage**. Five places used to read the keys directly, so a page
opened at `?zipcode=90210` still had its navbar and cart links enriched with
whatever the browser remembered.

| Storage | URL | Nav links now carry |
|---|---|---|
| 30303 / Atlanta | — | `zipcode=30303&location=Atlanta, GA` |
| 30303 / Atlanta | `?zipcode=90210` | `zipcode=90210` |

Note the dropped depot in row two: `Atlanta, GA` belongs to 30303, so carrying it
alongside a 90210 link would price delivery from the wrong yard. No depot beats
the wrong one.

`hooks/useStoredZip.ts` wraps it for components that need the SSR-safe mount read.

**Both `ZipLookup` components were deliberately left alone** — they already take
the URL value as an `initialZip` prop, and the listing one clears its field when
there is no parameter, which is intended behaviour rather than a gap.

### Guest lead capture

`GuestLeadModal` — a two-step quote on the PDP's Add to cart, for signed-out
visitors. Details first, one action (**Get Quote**), then the priced selection
with Continue shopping / Add to cart.

The second view is what makes the first fair: asking for contact details in
exchange for nothing is a toll gate on the buy button; asking in exchange for a
priced quote is a trade. The X and Escape still close it.

The quote rows are built in `ProductInfoPanel` from the values the summary
already renders, so the two cannot drift apart. The delivery address field runs
the same Geoapify lookup as everywhere else, and picking a suggestion re-prices
the quote for that address — without it, entering a Sacramento address against an
Atlanta depot showed $450 rather than the 2,474-mile route that is actually
call-for-rate.

**Reference listings** (`Generic Product Page`) now have an Add to cart button
that opens the quote form. They still cannot be bought, so step two drops Add to
cart and says a specialist will follow up.

## The Figma restyle

**Payment options** — three separated raised keys, red gradient on the selected
one, with the green *NO CREDIT CHECK REQUIRED* ribbon over Rent-To-Own.

**Specification options** — the selected key is a flat `#474747` face whose bevel
is six inset shadow layers; the resting keys are near-white with their own
gradient. Each carries what choosing it does to the price.

Those figures are derived, not copy: condition and grade are computed the same
way `sizePrices` already worked — hold the other axes still, take the cheapest
matching variant, express it against the current selection. On the Atlanta 40ft
HC the grades read Save $500 / $400 / $200 / Included, which is the real spread
between those variants.

**Summary** — flat under a red rule, with stock as a pill rather than a line of
text, since it is the one thing there that changes what the buttons can do.

**Ordering panel** — everything that commits the visitor moves onto one dark
slab. Corners square where it meets the summary, 30px where it ends. The three
actions carry the specified shadow stacks exactly; the quantity stepper is a
lighter slate tile holding two rounded keys.

**Reviews** — the PDP got its own section: heading and Google rating on one line,
then a row of cards. The rating badge and review data now live in one place each
(`components/shared/GoogleReviewsBadge.tsx`, `config/reviews.ts`) because the
homepage banner and this section had begun as separate copies of both.

## Mobile

**The header was the desktop typography on a phone.** Every size was fixed: the
page heading at 42px ran to seven lines, the product name at 45px Anton needed a
four-line clamp, the price sat at 52px. Reaching the specification options took
**1,627px of scrolling; it now takes 1,193px**. Desktop is byte for byte
unchanged, measured either side.

**Specification options** — labels move beside the options, which wrap through as
many rows as they need rather than holding a fixed three or four across.
Selected keys are outlined red on a phone and filled dark from `sm` up, per the
two designs.

**Summary and ordering panel run edge to edge**, breaking out of the section
gutter, with the slab losing its rounding at the top seam.

**New phone-only section** (`MobileTrustSection`) after the product: the call
banner, the monthly-payment routes, and four reassurance points. Desktop does
this work in the right-hand column, which a phone does not have.

## Bugs found and fixed

Pre-existing unless noted.

- **Every ZIP field could show — and save — "undefined".** `useGeoapify` built its
  label without the null guard its neighbours have, and Geoapify returns
  postcodes with no city. `selectResult` writes that label into `zipcode_label`,
  so `"undefined, GA 30345"` was persisted and read back on later visits.
- **Back desynced the URL from the page.** Variant changes pushed history entries
  with nothing listening for `popstate`, so the address bar said 40ft while the
  page showed 20ft. Now uses `replaceState`, so four size clicks cost one Back
  press to leave rather than four.
- **The gallery kept a stale image index across product swaps.** Harmless while a
  location change was a full navigation; with the component kept alive, image 4
  of six became `images[4]` of two.
- **One ZIP entry fired three depot lookups.** The auto-select effect re-ran on
  every result identity change.
- **The subtotal understated while delivery calculated.** For the few seconds a
  cold rate takes it showed $2,700 and then jumped to $3,150, while the delivery
  row above already read "Calculating…". It now says what it is missing.
- **Two `tel:` hrefs.** One passed the display number so it dialled with parens
  and spaces; the other wrapped `CONTACT_TEL` in another `tel:`, producing
  `tel:tel:8889779085`.
- **Introduced and caught by tests:** Escape left the quote modal on step two so
  the next open showed a stale quote; a missing `$` on the quote's delivery
  figure; the ZIP gate resolving `results[0]` rather than the row actually
  clicked.

## Demoing and testing

Both prompts are one-shot per browser by design, which makes either awkward to
show twice. Each has a URL parameter and a console function:

| URL | Console | Clears |
|---|---|---|
| `?reset-zip=1` | `resetVisitorZip()` | where the visitor is |
| `?reset-guest=1` | `resetGuestCapture()` | the captured lead |
| `?reset-all=1` | `resetDemoState()` | both |

The parameters strip themselves from the URL afterwards, so a link pasted into
chat does not reset on every open. Everything only clears that browser's own
storage.

**`resetVisitorZip()` deliberately leaves `userZipCode`.** `ZipAutoDetect` skips
itself while that key is set, so leaving it is what makes the reset hold — clear
it too and any browser with location permission already granted re-detects the
ZIP within a second, and the prompt never appears. Use
`resetVisitorZip({ includeGeolocation: true })` if you want the permission prompt
back.

Reference listings open the quote modal every time regardless of stored details,
so they are the reliable page to demo that one on.

## Also worth knowing

- **The ZIP prompt is an on-arrival interstitial.** Google treats intrusive
  interstitials as a mobile ranking signal and the PDP is an organic landing
  page. It is dismissible and gates genuinely useful pricing, but it is a
  tradeoff rather than free. Triggering on scroll or first interaction would
  sidestep it.
- **Delivery pricing still lives in WordPress.** The service is a deliberate
  bridge; when it moves to Django, replace the fetch and keep the exported
  signature — callers consume `DeliveryRatesResult`, not WordPress's shape.
- **A pre-existing hydration mismatch on the PDP.** `lib/linkEnrich.ts` appends
  `?zipcode=` to hrefs client-side, so breadcrumb and related-product links
  differ between server and client. React logs "this won't be patched up".
- **`useGeoapify` ships four `console.log` calls to production** and carries two
  pre-existing `set-state-in-effect` lint errors. Left alone deliberately —
  worth a cleanup pass of its own.
- **Two "Ideal for" images are ~2MB each** (`construction-sites.webp`,
  `disaster-relief.webp`) for a thumbnail rendering around 200px square.
  `next/image` resizes them, but they are worth downscaling at source.
